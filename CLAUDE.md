# AOCG AI Офис — фронтенд · инструкции для AI-агента

Постоянные правила для AI-агента (Claude Code). Соблюдать во всех сессиях. Это «оперативная память» репозитория — обновляется вместе с кодом.

## Что это за проект

Фронтенд платформы AOCG AI Офис — B2B SaaS для российского малого и среднего бизнеса. Управление первичными финансовыми документами и управленческим учётом. Мобильно-ориентированный интерфейс по образцу банковских приложений (Т-Банк, Альфа-Банк).

## Технологический стек

- React + Vite
- Иконки: lucide-react
- Графики: recharts
- QR: jsqr
- Хостинг: Railway (auto-deploy из main)

## Команды

- Запуск dev: `npm run dev` (localhost:5173, hot-reload)
- Сборка: `npm run build`

## Ключевые файлы

- `src/App.jsx` — весь UI, компоненты, роутинг (state-based, без URL-роутера). Это монолит, унаследованный технический долг — НЕ дописывать в него новое (см. раздел структуры ниже).
- `index.html` — Inter подключён, viewport-fit=cover
- `vite.config.js` — allowedHosts настроены

## Структура репозитория и лимиты на размер

Текущее состояние: весь интерфейс в одном `src/App.jsx` (несколько тысяч строк). Это долг, а не образец. Цель — не наращивать монолит, а постепенно разносить.

Куда класть новый код (для нового и при касании старого):

- Новый экран/раздел — отдельный файл в `src/pages/` (или `src/screens/`), НЕ дописывать в `App.jsx`.
- Переиспользуемый компонент (кнопка, sheet, баннер) — отдельный файл в `src/components/`.
- Логика запросов к API — в `src/lib/` (или `src/api/`), не размазывать fetch по компонентам.
- Кастомные хуки — `src/hooks/`.
- Статьи помощи — `src/help/` (md через react-markdown).

Правило при работе с App.jsx:

- Если правка затрагивает кусок `App.jsx` — по возможности вынести этот кусок в отдельный файл, а не редактировать на месте и не добавлять рядом. Дробим монолит по ходу дела, а не отдельным «большим рефакторингом».
- Новый функционал в `App.jsx` не добавлять в принципе.

Лимиты (сигналы пересмотреть, не жёсткие запреты):

- Компонент > ~200 строк → сигнал выделить под-компоненты или хук.
- Дублирование разметки/логики в 2+ местах → вынести в общий компонент.
- При приближении к лимиту — сообщить и предложить, как разнести, а не молчать.

## Терминология (строго)

- Платформа — AOCG AI Офис целиком
- Приложение — Прима, Финансы
- Модуль — только внутри Финансов (ДДС, ОПУ, Бюджет проекта)

## Приложение «Финансы» — модуль «Бюджет проекта» (фронт)

ТЗ: **AOCG-FIN-PBM-001 v0.1**. Это зеркало раздела «Приложение „Финансы“» в
CLAUDE.md бэкенда (репозиторий aocg-ai-office): там границы бэка и БД, здесь —
фронтовая часть.

**Границы (жёстко).** Весь фронт Финансов живёт в `src/finance/`. Код Примы
(чеки, отчёты, сканер, настройки) не трогать. Разрешённые касания вне зоны —
ровно два, оба минимальные:

- `src/App.jsx` — ОДНА ветка в существующем route-блоке: `/finance` →
  `<FinanceApp/>` из `src/finance/FinanceApp.jsx`. Внутренняя навигация Финансов
  живёт внутри FinanceApp, в App.jsx она не растёт.
- `src/lib/api.js` — новый файл: туда ВЫНОСИТСЯ `authFetch` (сейчас объявлен
  внутри App.jsx и не экспортируется), App.jsx начинает импортировать его
  оттуда. Дублировать authFetch в зоне Финансов запрещено.

`react-router` НЕ ставим — навигация остаётся самописной (pathname +
`history.pushState`), как в App.jsx сейчас.

**Раскладка `src/finance/`:**

- `FinanceApp.jsx` — точка входа зоны и внутренний роутинг модулей Финансов.
- `finance.css` — CSS-переменные зоны, собранные из палитры `src/lib/theme.js`.
  `src/index.css` НЕ трогать: там остатки шаблона Vite (акцент `#aa3bff`,
  `#root { width: 1126px }`), они общие с Примой — правка сломает её вёрстку.
- страницы и компоненты модуля — внутри зоны, по общим лимитам размера
  (компонент > ~200 строк → дробить).

**Десктоп-first.** Бюджет проекта — таблицы и своды, рабочее место за
компьютером. Нижняя таб-навигация и bottom-sheet'ы Примы (mobile-first) в зоне
Финансов не обязательны; мобильная вёрстка здесь — деградация, а не основа.
Дизайн-система общая (см. ниже): вишнёвый акцент (`--cherry`), Inter,
Cool Neutrals, `tabular-nums` на всех числах. Значения — только из ДС.

**Данные и права.** Все запросы — на `/api/finance/*` через `authFetch`.
org-scope и ролевой гейт (admin / manager (РП) / employee / accountant,
назначение на проект через `fin_project_members`) обеспечивает БЭКЕНД. Фронт
только отражает права в интерфейсе — фронтовый гейт защитой не считается.

## Параллельные сессии — не смешивать русла

Один заход Claude Code ведёт ОДНО русло работы — Прима **или** Финансы, не
одновременно. Оба контура живут в одном репозитории и видят рабочее дерево друг
друга; общие точки столкновения на фронте — `src/App.jsx`, `src/lib/api.js`,
`src/index.css`, `CLAUDE.md`.

- **Начало сессии:** `git status` + `git log -3`. Нашлись чужие незакоммиченные
  правки — сообщить пользователю ДО начала работы.
- **Конец сессии:** дерево чистое, всё закоммичено и запушено.
- **Стадировать** только свои файлы явными путями (`git add <файл>`), никогда
  `git add -A` / `git add .`.
- **Если параллельность неизбежна** — второму руслу отдельная ветка, не `main`.

Полная версия правила с разбором случая — в CLAUDE.md бэкенда
(репозиторий aocg-ai-office), раздел «Параллельные сессии — не смешивать русла».

## Дизайн-система

**Единственный источник значений — проект Claude Design «AOCG AI Office Design
System», файл `colors_and_type.css` (блок `:root`).** Машинные выгрузки оттуда:
`export/tokens.json` и `export/theme.js` (собираются `tools/build-tokens.js`).

**В этом файле конкретных значений цветов НЕТ и быть не должно.** Причина
записана кровью: раздел годами описывал два «фирменных» оттенка (Brand Mid
и Brand Soft), которых в дизайн-системе не существовало НИКОГДА. Их
пересказали по памяти, и они дважды просочились в код — в палитру круговой
диаграммы. Канон на этих ролях — `--cherry-ramp-2` и `--cherry-ramp-4`.
Документация, дублирующая значения, расходится с источником молча — поэтому
здесь только ссылка и правила. Разбор случая — задача T10 в трекере бэкенда.

Что где смотреть:

- палитра, шрифт, радиусы, тени, отступы — `colors_and_type.css` в ДС;
- превью групп — `preview/colors-*.html` (бренд, нейтральные, статусы,
  категории, диаграммы);
- локальная копия в коде — `src/lib/theme.js` (объект `C`). Сейчас пишется
  руками и покрывает лишь часть канона; переход на импорт выгрузки из ДС —
  задача T10 в трекере бэкенда.

Правила, а не значения:

- Новый цвет заводится В ДИЗАЙН-СИСТЕМЕ, не в коде. Понадобился оттенок,
  которого нет, — это вопрос к Claude Design, а не повод написать hex.
- Сырой hex в компонентах — временное состояние (258 литералов на 02.08.2026,
  вычищаются по T10). В новом коде брать значение из `C`, а не из макета.
- Обращение к несуществующему ключу темы (`C.bg`) даёт `undefined`, и стиль
  молча не применяется. Ловит сторож `scripts/check-theme-tokens.mjs`,
  подключён к `npm run lint` (задача T9).
- Шрифт: Inter (Variable, self-hosted), веса 400/500/600/700.
- Финансовые числа: всегда `tabular-nums`.
- Микро-анимации: opacity 100–180ms на тап.
- Safe-area inset для iOS Safari.

## Слои интерфейса (z-index)

Число слоя не выбирается на глаз — берётся из диапазона по РОЛИ элемента.
Правило появилось после разбора, где плавающая кнопка «Чеки» вообще не имела
слоя и оказывалась под оверлеями по случайности порядка в DOM, а меню
приложений (40/41) сталкивалось с кнопкой «Новый отчёт» (40).

| Диапазон | Роль | Примеры |
| --- | --- | --- |
| 1–39 | внутри страницы: липкие шапки, бейджи, подсветка | точки-разделители, свайп-действия карточки |
| **40** | **плавающие кнопки действия (FAB)** — ровно один уровень на все | «Добавить чек», «Новый отчёт» |
| 41–99 | всплывающее внутри страницы: меню, подсказки | меню приложений (50/51), «Ещё» в карточке чека (49/50), шторка внутри карточки (60) |
| 100–199 | модалки и шторки поверх страницы | Modal 100, детали отчёта 120, детали чека 150, выбор категории 160, BottomSheet 170, детали отчёта поверх чека 180 |
| 200–299 | полноэкранные режимы и уведомления | сканер 200, тосты 200 |
| 300–399 | подтверждения поверх полноэкранного | «сохранить как фото» 300, согласие 300 |
| 400+ | аварийное и системное | 400 |

Правила, а не пожелания:

- **Плавающая кнопка ВСЕГДА ниже любого оверлея.** Это инвариант: кнопка
  принадлежит странице, оверлей — поверх страницы. Не полагаться на порядок
  в DOM, задавать слой явно.
- **Новый оверлей берёт число из своего диапазона**, а не «на единицу больше
  соседнего». Соседа могут удалить.
- **Один уровень — одна роль.** Два элемента разных ролей на одном числе
  дерутся порядком в DOM, и результат меняется от любой правки разметки.
- Слой без комментария о роли — повод спросить, зачем он такой.

## Паттерны «делай»

- Использовать готовые библиотеки (lucide-react, recharts), не самописное.
- Segmented control для периода, bottom-sheet (выезжающая снизу панель) для выбора сотрудника — не dropdown.
- React автоматически экранирует `{переменная}` — это базовая защита от XSS.
- Атомарные коммиты, Conventional Commits.

## Сторожа и тесты: правило мутационной проверки (T11)

**Сторож, не проверенный мутацией, считается неработающим.** Добавили правило
линтера, проверку в `npm run lint`, guard-тест — сломайте то, что оно обязано
поймать, убедитесь, что прогон падает, верните как было. Зелёный прогон сам по
себе не отличает «всё чисто» от «ничего не проверено».

Два уточнения, оба куплены дорого:

- **Мутация нужна на КАЖДЫЙ заявленный источник.** Одна успешная мутация
  создаёт ложную уверенность обо всём стороже: она подтверждает одну ветку
  кода, а не сторож целиком. У `scripts/check-theme-tokens.mjs` источников
  три — объект `C`, локальные карты токенов в компонентах, канонный `theme`
  из `design/theme.mjs`; мутация нужна в каждый.
- **Зелёный прогон без охвата — не результат.** Сторож обязан уметь показать,
  ЧТО он проверил (`node scripts/check-theme-tokens.mjs --verbose` печатает
  файлы, карты и число проверенных обращений).
- **Мутация засчитывается только если она РЕАЛЬНО применилась.** Скрипт замены
  может не найти цель (шаблон не совпал, строка изменилась в прошлой задаче)
  и молча ничего не сделать. Тогда «сторож не поймал» читается как поломка
  сторожа, хотя ломать было нечего — и наоборот, «всё чисто» означает, что
  проверка не выполнялась. Замена делается с проверкой, что цель существует
  и текст изменился.
- **Мутация, выполненная НАПОЛОВИНУ, не засчитывается.** Если вторую половину
  нельзя проверить сейчас — нет данных, нет доступа, мешает CORS — правка
  НЕ считается проверенной. Пометить её непроверенной явно, а не обещать
  «проверю потом»: отложенная половина — ровно то место, где ошибка и живёт.
  Случай 02–03.08.2026: в c965ce4 первая половина (чипы фильтров перестали
  считаться дефектом) прошла, вторая (дефект «Главной» должен остаться) была
  отложена из-за CORS — и именно она содержала ошибку. Правка ослепила группу
  «шире родителя» ЦЕЛИКОМ на всех экранах, а таблица с нулями читалась
  как успех. Нашли сутки спустя, и только потому, что вторую половину
  всё-таки потребовали.

Три случая за один день 02.08.2026, каждый пойман только намеренной поломкой:

1. **T6** (бэкенд) — в FakePool общий шаблон SELECT перехватывал более
   специфичный запрос: тест прошёл бы при НЕработающем фильтре доступа.
2. **T9** — сторож токенов темы не покрывал `GlavnayaPage` и
   `OrganizationTab`: палитра приходит в них пропсом, а не импортом.
   Первый прогон дал честный ноль при дырявом охвате.
3. **T10, этап 1** — тот же сторож получил карту `theme` в список известных,
   но читать её не научился: регулярка ждала имена ЗАГЛАВНЫМИ. Прогон
   зелёный, проверено ноль обращений.

## Измеритель — такой же сторож: непроверенный, он врёт молча

Замер даёт ЧИСЛО, а число выглядит фактом независимо от того, что мерили.
Поэтому к измерителю применяется то же правило, что к сторожу: пока не
показано, что он меряет ИМЕННО ТО, он считается неработающим.

- **Пробный элемент обязан наследовать шрифт и контекст измеряемого.**
  Скрытый span, созданный рядом, по умолчанию берёт шрифт документа,
  а не элемента: те же четыре цифры он намерил 47.2px вместо 41.0 (16px
  вместо 13px). Число выглядело правдоподобно и прошло бы дальше.
- **Мерить лучше В МЕСТЕ, а не пробой рядом:** `getBoundingClientRect`
  и `scrollWidth` самого элемента не требуют воспроизводить контекст,
  потому что уже в нём. Проба нужна лишь тогда, когда измеряемого текста
  на экране ещё нет; тогда стили копируются явно и проверяются.
- **Сверять замер с картинкой.** Ошибку 03.08.2026 поймал скриншот:
  арифметика сходилась, а на экране стояло «•39…» вместо «•3950».
  Замер и скриншот — независимые свидетели, расхождение видно сразу.
- Признак того же класса: замер, который МЕНЯЕТ измеряемое (прокрутка
  ради видимости прячет плавающую кнопку и сдвигает полосу перекрытия).
  Если иначе никак — сказать об этом рядом с числом.

## Одноразовый скрипт тоже обязан проверять, что данные загрузились

Правило «нули читаются как результат» действует не только для прогона вёрстки,
где отказ вместо нулей уже встроен (T23), но и для любого разового скрипта
проверки. Пустой экран и пустые данные выглядят одинаково.

05.08.2026: скрипт диагностики зашёл на «Отчёты», увидел текст
«СОЗДАТЬ ПЕРВЫЙ ОТЧЁТ» и я объявил, что три отчёта пропали с прода. В базе
все три лежали на месте — список просто не загрузился (скорее всего упёрлись
в лимит 60 запросов в минуту после серии прогонов). Тревога стоила получаса
и закончилась запросом в прод-БД, который и надо было сделать первым.

Правило: перед любым замером скрипт проверяет признак загрузки (карточка,
сумма, счётчик) и при его отсутствии ПАДАЕТ, ничего не печатая. Вывод
«данные загрузились: да/нет» — в первую строку вывода. И отдельно: состояние
данных проверяется по ИСТОЧНИКУ (база, API), а не по тому, что нарисовано
на экране.

## Сокращённая запись `font:` — семейство обязательно

`font: 600 12px/1.1 inherit` — НЕ РАБОТАЕТ. В сокращённой записи последним
идёт СЕМЕЙСТВО, и `inherit` там недопустим: браузер отбрасывает объявление
целиком и молча, подпись рисуется системным шрифтом вместо Inter. Ни eslint,
ни сторож токенов, ни сборка этого не видят — увидеть можно только глазами
на экране или замером ширины текста.

Правило: в сокращённой записи всегда подставлять `${FONT}` из `src/lib/theme`
(`font: \`600 12px/1.1 ${FONT}\``). Наследовать шрифт — только отдельным
свойством `fontFamily: "inherit"`, оно валидно.

Поймано 05.08.2026 при сборке SwipeRow: подпись действия свайпа была задана
как `font: "600 12px/1.1 inherit"`, то есть де-факто вообще без шрифта.
Родня этому — правило про измеритель выше: и там, и здесь ошибка молчит
и выглядит правдоподобно.

## UX-принципы подсказок

- Подсказка = приглашение, не лекция. Появляется по запросу, не навязывается.
- Иконки `?` молчат до тапа, нейтральный серый, не отключаемые.
- Янтарные предупреждения — только при реальной проблеме, без мигания, отключаемые в Настройках.
- Onboarding — только при первом действии, с кнопкой «Не показывать снова», 2–3 шага максимум.
- Запрещено: подсказки при каждом действии, бейджи «новое!» на месяцы, неотключаемое обучение.

## Нормы РФ — закладывать проактивно, не реактивно

При любой задаче, касающейся фискальных данных, налогов, ПД, документооборота —
СНАЧАЛА свериться с действующей нормой РФ (стандарт ФФД/тег, статья НК, ФЗ),
заложить ПОЛНЫЙ набор значений по норме, а не только то, что встретилось в
текущих данных. Данные пользователя — подмножество нормы, не наоборот.
Примеры:

- НДС: тег 1199 ФФД = 12 значений (20/10/22/5/7/0/без НДС/расчётные 20-120,
  10-110, 5-105, 7-107, 22-122). Обрабатывать ВСЕ, не только встреченные.
- 152-ФЗ: данные граждан РФ — хранение в РФ (уже учтено).
- 54-ФЗ: реквизиты чека — по составу ФФД.
  Если норма неизвестна/могла измениться — проверить веб-поиском (источник:
  ФНС/КонсультантПлюс/НК), а не идти от данных.

## Рабочий процесс

- Одна фича — одна сессия, один атомарный коммит.
- Сначала план (plan mode), код не писать до одобрения.
- Показывать diff до применения; коммит — отдельной командой после проверки в браузере.
- UX-решения фиксировать ДО написания кода.
- После фронт-коммита — проверить, что новый бандл доехал до прода (по строковому маркеру, не по хешу бандла).
- После массовых замен проверять ЛИНТЕРОМ, не сборкой: Vite не ловит
  необъявленные имена. Скрипт замены переименовал ключи в файле, но не
  добавил туда импорт — `npm run build` прошёл, `npm run lint` упал
  с «'theme' is not defined» (T8).
- **Задача, которая трогает цвета или палитру, НАЧИНАЕТСЯ с подтяжки ДС**:
  взять свежий `export/theme.mjs` коннектором, положить в `design/`, обновить
  `design/source.json` и показать diff вендорной копии. Только после этого
  писать код.
  Почему именно так, а не по расписанию: копия защищена контрольной суммой от
  ручной правки, но не от УСТАРЕВАНИЯ — она бывает побайтно целой и при этом
  отставать от канона. Порог «старше N дней» не годится (время не связано
  с тем, менялась ли палитра, и предупреждение по календарю обучает себя
  игнорировать), а вот момент «сейчас буду красить» — точный: свежесть важна
  ровно тогда, и совершенно неважна при правке роутера.
  Класс не гипотетический: у Claude Design так отстали handoff-пакеты —
  значения совпадали байт в байт, но не хватало 40 токенов, и страницы внутри
  уже ссылались на `var(--surface-track)`, которого в копиях не было.

## Формат коммитов

`тип(scope): краткое описание`
Типы: feat, fix, chore, docs, refactor, test.
Пример: `feat(receipts): уплотнение фильтров, удаление бейджей`

## Чего НЕ касаться без явного запроса

- Конфигурацию Vite и деплоя.
- Общие компоненты шапки при правке отдельного экрана.
- Логику запросов к API без обсуждения.
